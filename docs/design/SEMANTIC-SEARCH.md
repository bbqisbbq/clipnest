# 语义搜索：先量，再决定

> 目标：剪贴板历史能**按意思**找到东西（"我记得复制过一段 nginx 反代的配置"），
> 而不是只能按字面匹配（现在的 FTS5 trigram 就是字面）。
>
> 这份文档先记录**落代码之前量到的数**，再写落地设计。所有数字都是在本机
> （DESKTOP-EQPTGVL，无独显）实测的，量法见 `scratch/embed-spike/`。

## 一、结论先行

| 问题 | 答案 |
| --- | --- |
| 硬件够吗 | 够。单条编码 **2.2ms**（p90 3.4ms），CPU 单核，无独显 |
| 要引向量库吗（FAISS/HNSW） | **不要**。1 万条暴力扫描 **4.8ms**，5 万条 25ms |
| 模型放哪 | 22.9MB INT8，跟 PP-OCR 一样做成**可选下载**，不背进安装包 |
| 存多少 | 每条 **512 字节**（int8），1 万条 5MB；量化对召回无可测影响 |
| 内存代价 | **+43MB**（会话 + 权重）→ 必须懒加载 + 闲置释放 |
| 质量够吗 | 够用但要配 FTS 融合：R@5 **67%**，R@10 **77%**，而同一批查询 FTS 命中 **0%** |

## 二、选型

**`BAAI/bge-small-zh-v1.5`**（ONNX INT8，`Xenova/bge-small-zh-v1.5` 的导出）

- 4 层 / 512 维 / 视觉 21128，中文专用，MTEB-zh 上性价比档位最好
- 词表 107KB + 模型 22.9MB，加起来还没 PP-OCR 的 det+rec 大
- 池化：**CLS**（不是 mean）；**不加**检索指令（见下）

跑过对照的替代方案：

| 配置 | R@1 | R@5 | R@10 | 结论 |
| --- | --- | --- | --- | --- |
| small + CLS | 41% | **67%** | 77% | ✅ 采用 |
| small + CLS + 官方检索指令 | 44% | 64% | 77% | 没净收益，且每条查询多 12 个 token |
| small + mean 池化 | 38% | 59% | 67% | 明显更差 |
| **base**（768 维 / 12 层 / 98MB）+ CLS | 46% | 64% | 77% | ❌ 4 倍体积、@5 反而更低 |

base 打不过 small 这件事值得记一笔：**这个任务的瓶颈不在模型容量**，而在
"短中文查询 ↔ 命令行/代码混排条目"这种跨形态匹配本身。

顺便否掉了 int8 的另一个动机：在 Go 里朴素 int8 点积**并不比 fp32 快**
（每元素要转 int32，1000 条时两者都是 0.54ms）。所以量化只买"省 4 倍空间"，
不要指望它提速。

## 三、实测数字

### 延迟（含分词）

| 项 | 数字 |
| --- | --- |
| 模型加载（冷） | 0.22–0.27 s |
| 单条编码 | 中位 **2.2ms**，p90 3.4ms（15–29 token 的剪贴板条目） |
| 分词 | 每千次 7.4ms ≈ **0.01ms/条**（可忽略） |
| 全量建索引 | 6ms/条 → 1 万条约 **1 分钟**（后台跑，一次性） |

### 暴力扫描（512 维内积）

| 条数 | int8 | fp32 | 存储/条 |
| --- | --- | --- | --- |
| 1,000 | 0.54 ms | 0.54 ms | 512 B / 2 KB |
| 10,000 | 4.82 ms | 6.61 ms | |
| 50,000 | 25.5 ms | 43.3 ms | |

结论：**"要不要向量数据库"是个伪问题**。剪贴板历史的量级（万级）用朴素循环
就够了，引 FAISS 只会换来一个重依赖和一套索引失效问题。

### 内存（PeakWorkingSet）

| 进程状态 | peak WS |
| --- | --- |
| 只有 onnxruntime（无模型） | 29.7 MB |
| onnxruntime + 模型（跑过 200 条编码） | 72.8 MB |
| **边际** | **+43.2 MB** |

当前应用常驻 120–180MB（Gate 2.5 闲置销毁之后）。+43MB 会把它推回 200MB 左右，
**所以这个模型不能常驻**：按需加载（首次语义搜索/建索引时），闲置几分钟后释放会话。

## 四、检索质量

评测集：39 条，覆盖运维 / 开发 / 本项目的领域 / 工作沟通 / 日常，
**每条查询都刻意避开目标条目的用词**（`scratch/embed-spike/bench_set.go`）。

| 指标 | 值 |
| --- | --- |
| Recall@1 | 16/39 = 41% |
| Recall@5 | 26/39 = 67% |
| Recall@10 | 30/39 = 77% |
| 同一批查询 **FTS 字面命中** | **0/39 = 0%** |
| 查询与目标共享 ≥3 字子串 | 1/39 = 3% |

也就是说：**这批查询现在一条都搜不到**，向量能把 2/3 的目标排进前 5。
这就是收益所在 —— 它不是在"替代" FTS，而是在补 FTS 完全够不着的那一半。

失败样例（诚实列出）：

| 查询 | 目标 | 名次 |
| --- | --- | --- |
| 看服务日志 | `journalctl -u clipnest -f` | 34 |
| 弹窗背景跟着主题变 | `DWMWA_USE_IMMERSIVE_DARK_MODE 亚克力…` | 27 |
| 写工作汇报 | `本周完成清洗结果下架留档接口…` | 26 |
| 装一个跑模型的库 | `pip install onnxruntime` | 23 |

规律：评测集里挤了一堆**长得很像的命令行条目**（docker/kubectl/journalctl/find/tar），
短查询在它们之间会挑错人。真实库里也一样 —— 所以融合必须保留 FTS 的名次，
不能"有向量就不用字面"。

### 一条重要的负面结论：**不要用绝对相似度阈值**

语料里根本没有答案的查询，最高分也到了 **0.45–0.49**，而正确答案里有 0.35 的。
绝对阈值分不开"没有相关条目"和"相关条目"。所以：

- 不显示"相似度 87%"这种数字给用户（没有意义）；
- 不做"低于阈值就报无结果"；
- 排序用**名次融合（RRF）**，不用分数加权。

## 五、落地设计

### 数据

```sql
-- 2.13.0
ALTER TABLE entries ADD COLUMN embedding  BLOB NOT NULL DEFAULT '';  -- 512×int8 + 4B scale
ALTER TABLE entries ADD COLUMN embed_hash TEXT NOT NULL DEFAULT '';  -- 编码时正文的哈希（内容变了就重编）
ALTER TABLE entries ADD COLUMN embed_state TEXT NOT NULL DEFAULT ''; -- ''|pending|done|failed|skipped
```

- 只索引**很可能被搜**的字段：`content` + `ocr_text` + `tags`
- 向量按内容哈希缓存：`embed_hash` 与当前正文哈希一致就跳过，否则重编
- 不写进同步包（向量是本机派生物，换机重算只要 6ms/条）

### 检索

```
用户输入 q
  ├─ FTS5(trigram) 取 top 50         ← 字面，保留原有行为
  └─ 向量扫描取 top 50                ← 语义
        ↓  RRF(k=60) 融合
     按融合分排序，走原来的 EntryQuery 过滤（标签/来源/时间/归档…）
```

RRF：`score(d) = Σ 1/(60 + rank_i(d))`。不用分数加权的原因是上面那条负面结论。

降级：模型没下载 / 没开 / 加载失败 → **只有 FTS**，界面一切照旧（和 OCR 的降级路径同构）。

### 编码队列

抄 `ocr_worker.go`：一条后台 worker，队列满了丢；启动后补扫历史条目（`embed_state <> 'done'`）。
建 1 万条要 1 分钟，所以必须后台、可中断、有进度。

### 内存

- 会话懒加载：第一次真需要（建索引或语义查询）时才建；
- `embedIdleRelease`：闲置 5 分钟后 `Destroy` 会话，把 43MB 还回去；
- 编码与查询共用同一个会话（加锁串行，编码 2ms 不值得并发）。

### 界面

**主界面零改动** —— 搜索框还是那个搜索框，只是搜得更到。可选加一个
「语义搜索」开关（默认开），关掉就是纯字面（有人就是要精确匹配）。

## 六、量法

```powershell
# 精度/召回/池化对比
go run ./scratch/embed-spike -cmd eval -pool cls
go run ./scratch/embed-spike -cmd eval -pool cls -quant      # int8 重排序
# 延迟 / 建索引 / 扫描
go run ./scratch/embed-spike -cmd bench
# 单条看分词对不对
go run ./scratch/embed-spike -cmd tokens -text "部署 nginx 反向代理"
# 真实库上的对比检索（FTS vs 向量）
go run ./scratch/embed-spike -cmd search -text "云端传不上去"
```

模型与词表放 `scratch/embed-model/`（不入库，脚本从 hf-mirror 拉）。
