# 语义搜索：先量，再决定

> 目标：剪贴板历史能**按意思**找到东西（"我记得复制过一段 nginx 反代的配置"），
> 而不是只能按字面匹配（现在的 FTS5 trigram 就是字面）。
>
> 这份文档先记录**落代码之前量到的数**，再写落地设计。所有数字都是在本机
> （DESKTOP-EQPTGVL，无独显）实测的，量法见 `scratch/embed-spike/`。

## 一、结论先行

| 问题 | 答案 |
| --- | --- |
| 硬件够吗 | 够。单条编码 **2.2ms**（p90 3.4ms），CPU 单核，无独显 |
| 要引向量库吗（FAISS/HNSW） | **不要**。1 万条暴力扫描 **4.8ms**，5 万条 25ms |
| 模型放哪 | 22.9MB INT8，跟 PP-OCR 一样做成**可选下载**，不背进安装包 |
| 存多少 | 每条 **512 字节**（int8），1 万条 5MB；量化对召回无可测影响 |
| 内存代价 | **+43MB**（会话 + 权重）→ 必须懒加载 + 闲置释放 |
| 质量够吗 | 够用但要配 FTS 融合：R@5 **67%**，R@10 **77%**，而同一批查询 FTS 命中 **0%** |

## 二、选型

**`BAAI/bge-small-zh-v1.5`**（ONNX INT8，`Xenova/bge-small-zh-v1.5` 的导出）

- 4 层 / 512 维 / 视觉 21128，中文专用，MTEB-zh 上性价比档位最好
- 词表 107KB + 模型 22.9MB，加起来还没 PP-OCR 的 det+rec 大
- 池化：**CLS**（不是 mean）；**不加**检索指令（见下）

跑过对照的替代方案：

| 配置 | R@1 | R@5 | R@10 | 结论 |
| --- | --- | --- | --- | --- |
| small + CLS | 41% | **67%** | 77% | ✅ 采用 |
| small + CLS + 官方检索指令 | 44% | 64% | 77% | 没净收益，且每条查询多 12 个 token |
| small + mean 池化 | 38% | 59% | 67% | 明显更差 |
| **base**（768 维 / 12 层 / 98MB）+ CLS | 46% | 64% | 77% | ❌ 4 倍体积、@5 反而更低 |

base 打不过 small 这件事值得记一笔：**这个任务的瓶颈不在模型容量**，而在
"短中文查询 ↔ 命令行/代码混排条目"这种跨形态匹配本身。

顺便否掉了 int8 的另一个动机：在 Go 里朴素 int8 点积**并不比 fp32 快**
（每元素要转 int32，1000 条时两者都是 0.54ms）。所以量化只买"省 4 倍空间"，
不要指望它提速。

## 三、实测数字

### 延迟（含分词）

| 项 | 数字 |
| --- | --- |
| 模型加载（冷） | 0.22–0.27 s |
| 单条编码 | 中位 **2.2ms**，p90 3.4ms（15–29 token 的剪贴板条目） |
| 分词 | 每千次 7.4ms ≈ **0.01ms/条**（可忽略） |
| 全量建索引 | 6ms/条 → 1 万条约 **1 分钟**（后台跑，一次性） |

### 暴力扫描（512 维内积）

| 条数 | int8 | fp32 | 存储/条 |
| --- | --- | --- | --- |
| 1,000 | 0.54 ms | 0.54 ms | 512 B / 2 KB |
| 10,000 | 4.82 ms | 6.61 ms | |
| 50,000 | 25.5 ms | 43.3 ms | |

结论：**"要不要向量数据库"是个伪问题**。剪贴板历史的量级（万级）用朴素循环
就够了，引 FAISS 只会换来一个重依赖和一套索引失效问题。

### 内存（PeakWorkingSet）

| 进程状态 | peak WS |
| --- | --- |
| 只有 onnxruntime（无模型） | 29.7 MB |
| onnxruntime + 模型（跑过 200 条编码） | 72.8 MB |
| **边际** | **+43.2 MB** |

当前应用常驻 120–180MB（Gate 2.5 闲置销毁之后）。+43MB 会把它推回 200MB 左右，
**所以这个模型不能常驻**：按需加载（首次语义搜索/建索引时），闲置几分钟后释放会话。

## 四、检索质量

评测集：39 条，覆盖运维 / 开发 / 本项目的领域 / 工作沟通 / 日常，
**每条查询都刻意避开目标条目的用词**（`scratch/embed-spike/bench_set.go`）。

| 指标 | 值 |
| --- | --- |
| Recall@1 | 16/39 = 41% |
| Recall@5 | 26/39 = 67% |
| Recall@10 | 30/39 = 77% |
| 同一批查询 **FTS 字面命中** | **0/39 = 0%** |
| 查询与目标共享 ≥3 字子串 | 1/39 = 3% |

也就是说：**这批查询现在一条都搜不到**，向量能把 2/3 的目标排进前 5。
这就是收益所在 —— 它不是在"替代" FTS，而是在补 FTS 完全够不着的那一半。

失败样例（诚实列出）：

| 查询 | 目标 | 名次 |
| --- | --- | --- |
| 看服务日志 | `journalctl -u clipnest -f` | 34 |
| 弹窗背景跟着主题变 | `DWMWA_USE_IMMERSIVE_DARK_MODE 亚克力…` | 27 |
| 写工作汇报 | `本周完成清洗结果下架留档接口…` | 26 |
| 装一个跑模型的库 | `pip install onnxruntime` | 23 |

规律：评测集里挤了一堆**长得很像的命令行条目**（docker/kubectl/journalctl/find/tar），
短查询在它们之间会挑错人。真实库里也一样 —— 所以融合必须保留 FTS 的名次，
不能"有向量就不用字面"。

### 一条重要的负面结论：**不要用绝对相似度阈值**

语料里根本没有答案的查询，最高分也到了 **0.45–0.49**，而正确答案里有 0.35 的。
绝对阈值分不开"没有相关条目"和"相关条目"。所以：

- 不显示"相似度 87%"这种数字给用户（没有意义）；
- 不做"低于阈值就报无结果"；
- 排序用**名次融合（RRF）**，不用分数加权。

## 五、落地设计

### 数据

**向量放旁表，不进 `entries` 行**（落地时改了初稿的方案）：

```sql
CREATE TABLE entry_vectors (
  id    TEXT PRIMARY KEY,
  hash  TEXT NOT NULL DEFAULT '',   -- 编码时正文的哈希（变了就重编）
  state TEXT NOT NULL DEFAULT '',   -- ''|pending|done|failed|unsupported|skipped
  vec   BLOB NOT NULL DEFAULT ''    -- 4 字节 scale + 512 字节 int8
);
```

初稿写的是给 `entries` 加三列。真动手时否掉了：`entries` 是同步与哈希的单一真源
（`entryColumns` / `scanEntry` / INSERT / 合并 / 指纹全围着它转），加三列要同时改
五六处，漏一处就是"存住了但读不出来"，而收益只是省一次 JOIN。旁表还白拿一个好处：
**"向量不同步"这件事天然成立**，不用在同步包里维护排除名单。

- 只索引**很可能被搜**的字段：`content` + `ocr_text` + `tags`
- 失效靠 `hash`：正文/OCR/标签任一变化就对不上，下一次对账会重编
- 不写进同步包（换机重算只要 6ms/条）

### 检索

```
用户输入 q
  ├─ FTS5(trigram) 取 top 100        ← 字面，行为与以前完全一致
  └─ 向量全量扫描取 top 100           ← 语义
        ↓  RRF(k=60) 融合，上限 200
     按融合分排序 → 走原来的 filters（标签/来源/时间/归档…）
```

三个实现上的取舍：

1. **排序倒着放**（名次最好的在数组末尾）。时间线是聊天式容器、列表自动贴底，
   正着放会让名次第 1 那条落在最上面被滚出可视区 —— 第一次 e2e 截图就是这个现象：
   "搜到了一屏结果，最相关的那个看不见"。倒过来正好贴在输入框上方。
2. **只给一页**：带 `before` 游标的相关性查询直接返回空（= 没有更多了）。
   相关性排序没有稳定的时间游标，硬凑下一页只会返回重复条目。
3. **降级靠"不做事"**：模型没下载/用户关了/这个构建没 cgo → `applyHybrid` 直接返回，
   查询原封不动走原路径。不是特例分支，是"没动过"。

### 编码队列与失效

抄 `ocr_worker.go`：一个后台 worker + 128 长的队列（满就丢）。失效**不靠钩子靠对账**：
启动后 20 秒、每次同步成功后各跑一次 `reconcileEmbed` —— 读全表的 (id, hash) 与
`entry_vectors` 比对，对不上就入队。这样即使某处写路径忘了挂钩子，后果只是"晚一会儿
更新"，不是"永远搜不到"。（保存条目与 OCR 完成这两处仍然显式入队，图的是即时。）

### 内存

- 会话懒加载：第一次真需要（建索引或语义查询）时才建，冷加载 0.25 秒；
- 闲置 5 分钟 `Close()` 会话，把 43MB 还回去；
- 编码与查询共用同一个会话（加锁串行，2ms 不值得并发）。

### 界面

主界面**零改动** —— 搜索框还是那个搜索框，只是搜得更到。设置里多一节「搜索」：
开关、索引进度（已索引 N 条 / 还有 M 条在编）、资源一键下载、以及"向量不外传"的说明。

### 资产

`embed-assets.zip`（23.9MB，解压 45MB：onnxruntime.dll + 模型 + 词表）放在本仓库的
pre-release `embed-assets-v1`，与应用版本解耦，不影响 `/releases/latest` 与自动更新。
URL 与 SHA256 写死在 `internal/clip/embed_assets.go` 里。

## 五之二、2.13.0 上线后当天的两个修正（2.13.1）

装出来第一天就翻了两处，都记在这儿，别再犯：

**1. `vec` 是 `BLOB NOT NULL`，而 nil `[]byte` 绑进去是 NULL。**
pending / failed / skipped / unsupported 这些"还没有向量"的状态传的都是 nil，
全部被 NOT NULL 拒掉 —— 整张表一行都没有，设置页永远「已索引 0 条」。

为什么单测没抓：`runEmbedForEntry` 里那次 pending 写失败是 `_ =` 忽略的，
而**资源齐全**时紧接着真编码成功、done 带着真 blob 写进去，用例照样全绿。
只有"资源缺失 / 编码失败"这条路才露馅 —— 也就是用户刚装完、还没下完的那段时间。
教训：**派生状态的写入失败不能吞**；另外测试要直接盯存储层，不要只走 happy path。

**2. 纯图片条目（正文只有 `![](memoimg:xxx)`）编出来是噪声。**
它们彼此的向量高度相似、和任何查询都半像不像，于是霸占结果头部 —— 实测用户库里
「草稿丢了怎么办」的前五条里四条是这种空图。现在 `entryVectorText` 先把图片令牌
剥掉，剥完没内容就记 skipped。

连带一个坑：只在 `runEmbedForEntry` 里判断"文本为空"是不够的 —— `reconcileEmbed`
必须先看 hash 而不是"文本是否为空"，否则**已经带着旧向量的 done 行永远不会重算**，
垃圾向量就留在库里继续霸占结果。所以 hash 改成对 `entryVectorText(e)` 计算：
提取规则一变，老数据自动失效重算。
