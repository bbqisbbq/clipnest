# ClipNest 2.9.3

这一版只做一件事：把"两台机器怎么都同步不上 / 删了又回来"背后的真问题修掉。
**没有新功能，装上后请重启一次 ClipNest**（老库的修复只在启动时跑一次）。

## 最要命的那个：删除从来不会传播

真机取证（坚果云 + 本机库）查出：老库的 `tombstones` 表还是旧主键 `PRIMARY KEY (hash)`，
而写墓碑用的是 `ON CONFLICT(hash, scope)` —— SQLite 会**整条拒绝**这条语句
（`ON CONFLICT clause does not match any PRIMARY KEY or UNIQUE constraint`），
当时的代码又把这个错误丢了，于是：

- 界面上删掉的条目，本机删了，**对端完全不知道**；
- 对端旧包里的同一份内容会被当"新增"传回来（"删了又回来"）；
- 实测：11-23 在界面上删了 17 条，`tombstones` 一条没多，远端包里的 `deleted` 也没变。

修法：启动时把这张表重建为 `PRIMARY KEY (hash, scope)`，老的 `scope='item'` 归到 `entry`
（这台机器因此有 22 条老墓碑从"不可见"变回"可见"），并且**写墓碑失败就让删除回滚**，
不再"删掉了但没留痕"。日志里会留一行 `tombstone schema migrated`。

## 其余五条

- **设备表终于有数字了**：PROPFIND 只请求 `<resourcetype/>`，坚果云就只回 resourcetype，
  所以"包大小"永远是 `0 B`、"最后更新"永远是 `—`。现在请求 `getcontentlength` /
  `getlastmodified` / `getetag`。要判断"对方到底有没有在写"，这两列比任何日志都直接。
- **一个坏对端包不再毒死整轮同步**：以前解析失败直接中断，那一轮既不合并其他设备、
  也不上传自己的包。现在跳过它、在结果行里写"N 个对端包读取失败已跳过"，其余照常。
- **失败会退避重试**：1 → 3 → 10 分钟，之后回到正常间隔。以前开机那一枪撞上网络没通
  就要白等 30 分钟。
- **`mkcol` 409 不再无限递归**（服务器对"已存在"回 409 而不是 405 时）。
- **保存设置不再重启同步循环**：设置页是自动保存的，以前改几个字段就连跑好几轮同步。

## 新增的"体检"

- **隔壁目录体检**：远端只有本机一个包时，顺手看一眼同账号、同级其他目录里有没有另一个
  `clipnest_data`，有就直接说"另一台机器的服务器地址很可能填成了 `…/dav/我的坚果云`"。
  这是"两台各写各的"最直接的解释。
- 同步目录里认不出的文件、附件在本机已丢失、附件超预算没上传，都会出现在结果行里。
- 设置页「云同步」终于会渲染 `panel.message`（列目录失败、只有本机一个包的具体原因，
  以前全被吞掉）。

## 已知边界

- 迁移前删掉的内容不会有墓碑（本机与远端都已经没有它们了）：**对端若还留着，会被当成新增
  传回来一次**，再删一次即可。
- 失败重试是退避而不是"立刻重来"，网络恢复后最多再等一个间隔（≤30 分钟）。
- 包里仍只带**最新 500 条**（`syncMaxEntries`），更老的历史留在本机、不上云。
